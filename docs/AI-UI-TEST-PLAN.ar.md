أنت وكيل اختبار UI. نفّذ هذا الملف على المشروع `newnew/zu-lms` كاملاً، وسلّم أدلة فعلية لكل نتيجة. المطلوب اختبار ما يراه المستخدم وما يضغطه وما يُحفظ فعلياً، بجميع الأدوار والحالات، وليس إرسال طلبات HTTP بدلاً من استخدام الشاشة.

- الجذر على الجهاز الحالي: `C:\Users\VIP\Documents\ChatGPT\New project\newnew\zu-lms`.
- الحزمة الحاكمة، نسبةً إلى الجذر: `../zu-lms-build-packمعتمد/zu-lms-build-pack/`؛ اقرأ ملفات `00` إلى `12` و`QUESTIONS.md` كاملة.
- مرجع الشكل: `prototype/` ثم `template/paces/`. تعليمات الشكل التفصيلية في الملف المجاور `AI-FRONTEND-IMPLEMENTATION.ar.md`.
- افحص أولاً النسخة الحالية، ثم أعد الاختبار بعد إعادة التصميم. لا تخلط أدلة النسختين.
- مهمتك الأصلية الاختبار والتوثيق. لا تغيّر قواعد الباك إند أو قاعدة البيانات أو الصلاحيات لإنجاح حالة. إصلاح الواجهة، إن كُلّفت به، يخضع حصراً لحدود ملف الفرونت.
- المتطلبات غير المنفذة = `FAIL/MISSING`، والتبعيات غير المتوفرة = `BLOCKED`؛ لا تستبدلها بـ PASS أو تخفها من المقام.
- جداول هذا الملف إلزامية، ويُضاف إليها كل عنصر تفاعلي فعلي يكشفه الجرد. عبارة «كل شيء» تُثبت بتغطية الجرد، لا بعدد اختبارات مختار مسبقاً.

### أولوية الحكم

الحزمة المعتمدة أولاً؛ قرارات المستخدم الصريحة الموثقة ثانياً فيما تحسمه؛ الكود دليل على الوضع الحالي وليس مصدراً لتغيير المتوقع؛ البروتوتايب مرجع بصري فقط. بعض نصوص الحزمة نفسها تتعارض: سجّل التعارض ومصدرَيه والحالة المتأثرة `BLOCKED-SPEC` ولا تحسمه بصمت. مثال: عمود الأدمن في بعض صلاحيات الاحتياجات مقابل وصف وجهة المراجعة التشغيلية للجودة؛ اختبر الواضح وسجّل المتعارض منفصلاً.

## 1. ما ثبت من قراءة النسخة الحالية

هذه ملاحظات مصدرية بتاريخ إعداد الملف؛ أعد التحقق منها قبل التنفيذ، ولا تعتبرها نتائج متصفح:

1. `docs/implementation-progress.md` يذكر 322 فحص HTTP و70 اختبار .NET وبعض الحوارات فقط، ويصرّح بأن UAT الكامل لم يُنجز. لا تعِد استعمال هذه الأرقام كدليل UI.
2. غالبية الصفحات في `src/ZuLms.Web/Pages/`، والعامة في `Areas/Public/Pages/`؛ لا تفترض أن كل الأدوار موجودة في Areas كما تصف الحزمة.
3. `_Layout.cshtml` يحمّل `app.css` و`site.css` ولا يحمّل طبقة `prototype/css/experience.css`؛ توجد نصوص عربية ثابتة في القوائم.
4. `Pages/Courses/Details.cshtml` و`Pages/Shared/_DirectCourseForm.cshtml` يحتويان حقول تاريخ أصلية، رغم منعها في الحزمة.
5. `Pages/Shared/Profile.cshtml` يحتوي سكربتاً inline؛ افحص تحميل الملف مع CSP الفعلي، لا تفترض أن API ناجح يعني ظهور البيانات.
6. `wwwroot/js/site.js` يوفّر `ZuLms.ui.confirm/prompt/show` بواسطة `<dialog>`؛ اختبرها كلها. المشكلة السابقة كانت أن prompt الأصلي غير مدعوم في متصفح مضمّن.
7. `pickers.js` يعتمد على jQuery + Moment + daterangepicker؛ بعض الصفحات تحملها وبعضها لا. اختبر كل تاريخ داخل كل حوار أيضاً.
8. قاعدة التشغيل السابقة تضم بيانات جامعة حقيقية. لا تشغّل الاختبارات المتلفة أو الإرسال الجماعي عليها.

## 2. التحضير والتشغيل بالترتيب

### 2.1 تجميد خط البداية

1. اضبط Working Directory إلى جذر `zu-lms` أعلاه.
2. سجّل تاريخ التنفيذ، commit إن وُجد، حالة Git، نسخ .NET والمتصفح وNode، نظام التشغيل، قاعدة الاختبار ومخططها، مسار التخزين، URL، اللغة والمنطقة الزمنية.
3. المستودع الأب حالياً قد يعرض المشروع كله Untracked؛ لذلك `git diff` وحده لا يكشف التغييرات. احفظ قائمة الملفات وبصمات SHA-256 للمصدر قبل الجولة، واستثنِ `bin/obj/logs` وأدلة الاختبار. احتفظ بخط الأساس خارج المصدر.
4. اقرأ `global.json` و`Directory.Packages.props` و`deploy/.env.sample` و`tools/api-tests/run-app.ps1` قبل تشغيل أي سكربت.
5. لا تنسخ كلمات المرور الموجودة في أدوات التطوير إلى التقرير أو اللقطات. استخدم أسرار اختبار من البيئة وأسماء وهمية صريحة فقط.

### 2.2 بيئة بيانات معزولة

1. وفّر قاعدة PostgreSQL اختبار مستقلة، وتخزين ملفات مستقل، وصندوق SMTP اختبار يلتقط الرسائل دون إرسال لأشخاص حقيقيين. التشغيل يطبّق الهجرات والبذرة تلقائياً؛ اضبط الاتصال **قبل** بدء التطبيق.
2. عيّن في جلسة التشغيل `ZU_DB_CONNECTION` و`ZU_ENC_KEYS` و`ZU_JWT_KEY` و`ZU_STORAGE_ROOT` و`ZU_PUBLIC_BASE_URL` و`ZU_BOOTSTRAP_ADMIN_*`. القيم الحقيقية تُؤخذ من بيئة الاختبار، لا من هذا المستند. `ZU_ENC_KEYS` يتبع JSON الحزمة وJWT مفتاحه بالطول المعتمد.
3. اضبط `ASPNETCORE_URLS` إلى `https://localhost:7275` وبيئة Development للاختبار المحلي، مع شهادة تطوير موثوقة. استخدم `localhost` في المتصفح؛ المنفذ وحده لا يعزل كوكيز مشاريع على المضيف نفسه.
4. سكربت `run-app.ps1` يعود افتراضياً لقاعدة `zu_lms` إن غاب المتغير؛ ممنوع تشغيله بهذه العودة في جولة تغيّر البيانات.
5. سكربت `seed-fixtures.mjs` يجهز **ثلاثة** موظفين فقط، يكتب في `zulms_rebuild`، ويستخدم مفتاح تشفير تطوير ثابتاً، ويعتمد على كلية موجودة. لا يكفي لجميع حسابات هذا الملف، ولا يعمل تلقائياً مع مفتاح عشوائي أو قاعدة فارغة. قبل استعماله: راجع إعداداته ومطابقتها ثم استخدمه في قاعدة اختبار فقط. عند عدم التطابق جهّز Fixtures متوافقة في أدوات الاختبار، دون تعديل خدمات التطبيق.
6. جهّز الهيكل والموظفين الوهميين عبر مصدر جامعة محلي وهمي مطابق للعقد في `04` ثم شغّل المزامنة من UI. إن لم تتوفر هذه الوسيلة أو Fixtures معتمدة: سجّل حظر إعداد البيانات، ولا تستخدم موظفين حقيقيين كبديل.

### 2.3 أوامر الفحص الأساسية

نفّذ كل أمر منفرداً من جذر المشروع وسجّل exit code. إعداد متغيرات البيئة السابقة شرط مسبق:

```powershell
dotnet --info
dotnet restore ZuLms.sln
dotnet build ZuLms.sln -c Release
dotnet test ZuLms.sln -c Release --no-build
```

اختبارات PostgreSQL تحتاج Testcontainers/Docker أو `ZU_TEST_PG` منفصلاً ومخصصاً للاختبارات. راجع Fixtures الاختبارات قبل تحديد الاتصال؛ لا توجّه اختبار إعادة إنشاء/حذف قاعدة إلى قاعدة UAT أو التشغيل. PostgreSQL 18 البديل المحلي لا يثبت بوابة PG17 المطلوبة في الحزمة.

بعد إعداد بيئة التطبيق، إن كان المنفذ خالياً:

```powershell
powershell -NoProfile -File tools/api-tests/start-local.ps1 -Configuration Release
```

هذا السكربت قد يعيد استخدام عملية موجودة؛ نجاح health لا يثبت أنها النسخة الجديدة أو قاعدة UAT. طابق PID ومسار executable ووقت التشغيل وإعداد الاتصال مع خط الأساس. عند الحاجة لإعادة تشغيل عملية هذا المشروع افعل ذلك وحدها، دون قتل كل عمليات dotnet.

7. افتح `/health` ثم `/login` عبر HTTPS. افحص Console وNetwork والأصول المحلية، ثم ادخل بالأدمن الوهمي.
8. إذا تعذر تشغيل الاختبارات أو HTTPS أو المتصفح، وثّق السبب وخطوة الإصلاح المطلوبة، ولا تواصل بنتائج مصطنعة.

### 4.2 فروق كتالوج الحزمة: افحصها صراحة

الحزمة تطلب أيضاً `/admin/users/{id}`, `/admin/roles`, `/admin/stats`, `/quality/external-instructors`, `/quality/courses/new-historical`, `/dean/stats`, `/account/settings`، ومسارات تفاصيل الدورات الخاصة بالأدوار، و`/member/available`, `/member/enrolled`, ومسارات `/instructor/courses/{id}/attendance|exam|impact|evaluation`.

1. جرّب كل مسار مطلوب مباشرة ومن رابط الواجهة؛ افحص `Program.cs` وroutes لتأكيد أي alias قبل القول إنه مفقود.
2. إن وُجدت الوظيفة مدمجة في صفحة أخرى، اختبرها هناك وسجّل `FUNCTION-PASS / ROUTE-GAP`؛ لا تمنح المسار المطلوب PASS.
3. إن لم توجد الوظيفة ولا API يدعمها، سجّل `MISSING-FEATURE` مع مقتطف المتطلب. لا تختلق صفحة ساكنة لإنهاء الجرد.
4. لا تُلزم وكيل الفرونت بإعادة تنظيم Areas أو تعديل routing الخادم ضمن مهمة الشكل.

## 5. وصفة الاختبار المشتركة لكل عنصر

لكل حالة في الجداول التالية، نفّذ: **تهيئة → فتح من UI → إجراء → تحقق مرئي → تحقق Network → refresh/إعادة فتح → تحقق الأثر في الدور الآخر والسجل حيث يلزم**. API للتهيئة أو التثبت المساند مسموح؛ الإجراء محل الحكم يجب أن يحدث من UI. لا تعدّ fixture سبق إنشاؤها دليلاً على نجاح زر الإنشاء.

للحالات 400/401/403/404/409/422/429/500: استخدم سبباً حقيقياً في البيئة إن أمكن. محاكاة الرد من أداة المتصفح تُستخدم لفحص طريقة عرض الخطأ فقط، وتوسم `SIMULATED-UI`؛ لا تثبت صلاحية أو قاعدة عمل في الخادم. انقطاع الاتصال بعد كتابة غامضة النتيجة: تحقق من السجل قبل إعادة المحاولة، ولا تقبل إنشاءً مكرراً.

### حساب الإحصاءات المهنية على بيانات معلومة

جهّز M1 في F1 له شهادتان معتمدتان نشطتان (واحدة منتهية)، M2 في F1 له واحدة سارية، M3 في F2 له ثلاث سارية، مع شهادة Submitted وأخرى معطلة لا تحتسبان. متوقع إجمالي الشهادات 6 مع المنتهية و5 دونها؛ أصحاب شهادة 3؛ أعلى عضو M3 ثم M1 ثم M2 (دون المنتهية تعادل M1/M2 يُحسم بالاسم). متوقع F1=3 وF2=3 مع المنتهية، ثم F1=2 وF2=3 بدونها. المتوسط والتغطية يحتاجان مقام السكان الذي يحدده عقد الخدمة؛ سجّل المقام الفعلي الواضح من المواصفات/DTO، ولا تفترض أن `members` يعني جميع حسابات الجامعة إن لم يحسم العقد ذلك. إذا بقي غامضاً سجّل تعارضاً بدلاً من حساب يخفيه.

| AUX07 | جرس كل دور: 0 ثم 1 ثم >20 إشعار، افتح المصدر، read/read-all، refresh | عدد غير المقروء صحيح وآخر 20؛ لا إشعار لنفس المنفذ ولا اطلاع على إشعار غيره |
| AUX08 | مصدر إشعار أصبح معطلاً/غير مصرح بعد صدوره | صفحة منع/رسالة مفهومة دون تسريب أو 500 |
| AUX09 | dashboards/stats الجامعة/كلية/دورة/عضو؛ كل فلتر ورسم وتفاصيل | مطابقة الأرقام لFixtures والخادم؛ لا جمع جلسات دورات مختلفة في رسم واحد |
| AUX10 | اختر دورة A ثم B في رسم الحضور/التقييم | عنوان رمز واسم الدورة ومصدر الرسم يتغيران معاً؛ جدول بديل قابل للقراءة |

## 13. مصفوفة الصلاحيات المطلوبة

لا يكفي اختبار أدمن ثم عضو فقط. لكل Route ولكل Action في الجرد:

1. أنشئ صفوف A/Q/D/I-internal/E/M/Anonymous، ثم MultiRole وOverride Allow/Deny/Inherit.
2. لكل دور اختبر المورد داخل نطاقه وخارجه حيث ينطبق: كلية أخرى، دورة أخرى، مستخدم آخر، ملف آخر، محاضرة أخرى.
3. تحقق من: ظهور القائمة، فتح URL، ظهور/تمكين الفعل، نتيجة طلب فعلي، عدم تغيّر البيانات عند الرفض.
4. استخرج المتوقع من مفاتيح `03 §11` وقيود `05..12`، لا من كون المستخدم يحمل اسم Admin. الدورات التي تديرها الجودة لها نطاق خاص، والخارجي لا Member ولا Shared.
5. منع افتراضي صريح: اقتراح ورفع احتياج لغير العميد؛ أسماء مشاركين للعميد؛ بناء نموذج تقييم للمحاضر؛ QR حضور؛ درجات رقمية؛ حذف تشغيلي فعلي.
6. اختبر رابط تنزيل محفوظاً بعد الخروج أو سحب الصلاحية، لا URL الصفحة فقط.
7. نجاح الوصول إلى غلاف HTML بلا بيانات لا يكفي لاجتياز/رفض نطاق؛ افحص الردود والبيانات المرئية والطلبات.

## 14. العرض والاستجابة وإتاحة الاستخدام

### مصفوفة العرض الإلزامية

- Chromium: **كل صفحة وكل حوار وكل فرع شرطي** بالعربية والإنجليزية عند `1440×900` و`390×844`.
- كل صفحة عند `320×568`, `768×1024`, `1024×768`, `1920×1080`، في الاتجاهين؛ افتح كل حوار مرة على الأقل عند العرض الأصغر.
- Firefox وWebKit إذا توفرت الأدوات: كل صفحة تحميل/تنقل، وكل مكوّن تفاعلي مشترك، والرحلات AUTH02 وCRS03–04 وATT04–07 وCERT01 وPRO04–05. المتصفح غير المتوفر = BLOCKED، لا تدّعِ cross-browser PASS.
- Zoom 200%، لوحة مفاتيح فقط، reduced-motion، نظام تشغيل يفضّل dark (يبقى التطبيق فاتحاً).

### خطوات الفحص لكل شاشة

1. التقط full-page وصورة viewport بالحالة المحملة؛ افتح الحوارات والقوائم ومنتقي التاريخ وخذ لقطة لكل حالة مهمة.
2. تأكد أن عرض document لا يتجاوز viewport؛ التمرير الأفقي داخل غلاف الجدول فقط. لا تستخدم قص body لإخفاء قص عناصر.
3. القائمة الجانبية تفتح وتغلق بالزر والخلفية وEscape، ولا يتسرب التركيز/التمرير خلفها؛ تبديل الاتجاه يعكس موضعها.
4. الهيدر لا يتراكب؛ مبدّل السياق واللغة والجرس والخروج متاحون على الهاتف؛ اسم طويل لا يدفع الأزرار خارج الشاشة.
5. جميع inputs لها label واسم قابل للوصول؛ الأيقونات التفاعلية لها accessible name؛ لا تعتمد الحالات على اللون وحده.
6. تباين النص العادي ≥4.5:1، الكبير ≥3:1، حدود ومؤشرات التفاعل ≥3:1 حيث تنطبق؛ التركيز مرئي ولا تحجبه sticky bars.
7. Tab/Shift+Tab وEnter/Space والأسهم للتبويبات؛ روابط وأزرار حقيقية وليست div قابلة للنقر بلا لوحة مفاتيح.
8. عند فتح modal ينتقل التركيز داخله ويعود للمشغّل؛ رسائل الأخطاء تُعلن، والـtoast لا يخفي نتيجة مهمة قبل قراءتها.
9. أكواد الحضور والبريد والمرجع LTR داخل RTL؛ الأرقام 0–9؛ واجهة EN كاملة مع fallback عربي للمحتوى الذي لا ترجمة له فقط.
10. كل رسم له عنوان ونطاق وفترة وlegend وبديل نصي/جدول؛ الصفر واللا بيانات يختلفان عن فشل التحميل.
11. لا CDN/خط خارجي/صورة مكسورة. احظر الإنترنت الخارجي مع إبقاء localhost ثم أعد فتح الصفحات؛ الواجهة المحلية تبقى تعمل.
12. قارن الشكل مع الصفحات المرجعية وتوكنات ملف الفرونت، ولا تعتمد snapshot مأخوذاً من واجهة معيبة كمرجع جديد دون مراجعة.

## 15. تنفيذ الأتمتة إن توفرت أدواتها

- استخدم أداة المتصفح المتاحة بالفعل؛ لا تضف npm/NuGet لمجرد التفضيل. Playwright إن كان متاحاً يمكنه تنفيذ نفس الحالات. إن احتاج تثبيت حزمة غير معتمدة سجّلها في QUESTIONS وانتظر حسم تلك النقطة، وواصل اختبار المتصفح المتاح.
- جهّز حالات ببيانات منفصلة وسياقات منفصلة. لا تشغّل تعديلات الإعدادات أو نشر نموذج التقييم أو تغيير الأدوار بالتوازي على نفس القاعدة.
- فضّل locator بالـrole/label؛ للصفوف المتكررة استعمل ID السجل في data attribute ثابت. لا تعتمد nth-child أو نص متغير للترجمة.
- انتظر استجابة العملية المحددة ثم assertion للنتيجة المرئية، لا `sleep(5000)` عاماً ولا `networkidle` لصفحات تستطلع باستمرار.
- أخطاء Console غير المتوقعة تفشل الحالة. لا تتجاهل فشل selector بـtry/catch صامت ولا تعِد الاختبار مراراً حتى يمر ثم تخفي المحاولات.
- احفظ trace/screenshot عند الفشل ومع كل بوابة مرحلة؛ اخفِ الأسرار قبل الحفظ، خصوصاً credentials.reveal.
- لا تسجل responses كاملة تحتوي بيانات خاصة؛ احتفظ بالـmethod/path/status/errorCode/correlationId بعد التنقيح.
- عند اعتماد baselines مرئية ثبّت البيانات والوقت والخطوط وحجم الشاشة؛ استثنِ فقط أجزاء ديناميكية مبررة، لا كامل الجدول أو الكود محل الاختبار.

## 16. ترتيب الجولات وإعادة الفحص

1. PREP: البيئة + البيانات + الجرد + البصمات.
2. SMOKE: login لكل دور، shell، dashboard، قائمة ودورة وملف، Console/Network. لا تتوقف عن توثيق الأعطال إذا فشل smoke، لكن لا تبدأ رحلات تعتمد على مكوّن معطل.
3. AUTH/ADM ثم CRS ثم ATT/EXM ثم EVAL/IMP/CERT ثم NEED/PRO/PROF ثم AUX.
4. نفّذ مصفوفة الصلاحيات، الأخطاء/التزامن، ثم عرض/لغات/متصفحات لكل ما سبق.
5. بعد كل إصلاح: أعد الحالة الفاشلة وحالات المكوّن المشترك المتأثرة. بعد تغيير shell/api/pickers/modals: أعد smoke لجميع الصفحات واللغتين، لا صفحة الإصلاح فقط.
6. الجولة النهائية على build واحد معروف: السيناريوهات كاملة، والاختبارات .NET المطلوبة، ومراجعة تغييرات الملفات.

## 17. الدليل والحكم النهائي

### قالب حالة الاختبار

```text
ID / Requirement / RunID / Build:
Role + account alias / route / browser / viewport / lang / timezone:
Preconditions + fixture IDs + settings:
Steps (numbered):
Expected per step:
Actual per step:
Request method/path/status (no secrets):
Persisted result after reload:
Cross-role / audit / notification evidence:
Screenshot/trace paths:
PASS | FAIL | BLOCKED | NOT-RUN | N/A:
Defect ID / cleanup performed:
```

### قالب العيب

`UI-BUG-###`، العنوان، الأولوية، المتطلب، الإصدار/الدور/المسار، خطوات إعادة إنتاج دقيقة، المتوقع مقابل الفعلي، صورة/trace، console/network المنقح، ملفات محتملة، هل السبب UI أم عقد/خادم أم بيئة، أثره على الحالات التابعة، وخطوات إعادة الاختبار. لا تصف عيباً مصدره التخمين كعطل متصفح مثبت.

### شرط الانتهاء

- 100% من المسارات المطلوبة والفعلية والعناصر التفاعلية والحالات في هذا الملف مرتبطة بسجل نتيجة؛ لا مسار أو زر بلا حكم.
- كل حالة واجبة PASS، أو تقرير صريح أن القبول غير مكتمل مع قائمة FAIL/BLOCKED/NOT-RUN. ممنوع «كل UI يعمل» مع حالة غير ناجحة أو ميزة ناقصة.
- `PASS rate = PASS / كل الحالات الواجبة`؛ BLOCKED وNOT-RUN لا يُحذفان من المقام. N/A له سبب ومراجعة مستقلة.
- لا عيوب حرجة أو عالية أو متوسطة مفتوحة لقبول كامل؛ العيوب البصرية الباقية تُذكر بوضوح ولا تُخفى وراء نجاح API.
- القالب الحقيقي وSMTP الحقيقي وبوابة PG17 تُذكر بحكم منفصل؛ نجاح تدفق UI بقالب وصندوق تجريبي لا يثبت تلك الاعتمادات الخارجية.
- سجّل استعادة الإعدادات والـoverrides وسياقات الاختبار وإيقاف المصدر الوهمي. لا تمسح audit ولا تحذف بيانات تشغيل فعلياً لإخفاء آثار الاختبار.
- سلّم `summary.md` بجدول النتائج حسب الدور/الميزة/اللغة/المتصفح، فجوات الحزمة، العيوب، الأدلة، وما يحتاج وكيلاً آخر. لا تستبدله بجملة «تم الاختبار بنجاح».
